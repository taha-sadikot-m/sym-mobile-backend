# Deploying the SYM mobile backend

The backend runs on Render in Virginia, next to the Neon database (us-east-1). `render.yaml` describes it as a
blueprint with two services that share one environment group (`sym-mobile`):

| Service | What it is |
|---|---|
| `sym-mobile-backend` | The API and admin console (Docker, `/health` check, `alembic upgrade head` before every deploy). |
| `sym-mobile-jobs` | A cron job, every 5 minutes: `python -m app.jobs` (debate reminders; the daily data clean-up). |

## First deploy

1. **Code:** push this repository to GitHub (`sym-mobile-backend`, branch `main`).
2. **Database login:** in Neon, create a dedicated login for this service. Use the **pooled** connection string
   with the asyncpg driver:
   `postgresql+asyncpg://<user>:<password>@<host>-pooler.<region>.aws.neon.tech/<db>?ssl=require`
   (Production should use the least-privilege `sym_mobile` role; see the README.)
3. **Blueprint:** in Render, choose New → Blueprint, pick the repository, and fill in the secret values it asks for:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | The pooled connection string above. |
   | `RESEND_API_KEY`, `RESEND_FROM_EMAIL` | From Resend. The sender domain must be verified there. |
   | `GEMINI_API_KEY` | Google AI Studio key. Check its **spend cap** (at ai.studio/spend) is high enough. |
   | `DEEPGRAM_API_KEY` | From Deepgram. |
   | `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` | From LiveKit Cloud. |
   | `EXPO_ACCESS_TOKEN` | Only if "Enhanced push security" is turned on in the Expo project; otherwise leave it empty. |
   | `SUPPORT_EMAIL` (optional) | The contact address shown on `/privacy` and `/terms`. |

   `SECRET_KEY` and `JWT_SECRET` are generated by Render. `TRUSTED_PROXY_HOPS=1` must stay as set: it makes rate
   limits and audit logs use the real client address.
4. **Check:** open `https://<service>.onrender.com/health`. It should say `"status": "ok"` with `"web_tables": "ok"`.
   If the web team changed a shared table, the deploy stops here and Render keeps the old version running
   (see "Web table changes" below).
5. **First admin:** open the service's Shell in Render and run
   `python -m scripts.create_admin --email you@symedu.in --name "Your Name" --role super_admin`, then sign in at
   `/admin` and set up the authenticator app.
6. **Jobs:** in the admin console, open Notifications → Scheduled jobs. After 5 minutes both jobs should show a run.
   "Run now" runs them immediately.
7. **App:** build the app with `EXPO_PUBLIC_API_URL=https://<service>.onrender.com` (set in `eas.json` for the
   `preview` and `production` profiles in the app repository) and sign up with a real email address to check
   that codes arrive.

## Push notifications

The server sends through Expo's push service, which forwards to Apple and Google. The app needs credentials for each:

- **Android:** a Firebase project with an Android app for `in.symedu.mun`, and its FCM v1 service-account key
  uploaded in Expo (`eas credentials` → Android → Google Service Account Key for push notifications).
  Without it, Android devices can't get a push token, and the app quietly skips notifications.
- **iOS:** `eas build` creates the Apple push key automatically when you build for iOS.

Notifications only work in installed builds. They don't work in Expo Go on Android or in the web preview.

## Releasing a change

Merge to `main` and Render deploys automatically, running migrations first. A failed migration or a changed web
table stops the deploy and the previous version keeps running. Migrations must only touch the `mobile` schema
(enforced by `migrations/env.py`).

## Web table changes

`app/web/contract.py` lists every column of the five shared website tables that this backend uses. If the web team
renames or removes one, the deploy stops with "Web tables changed: …". To fix it:

1. Refresh `db/web_schema.sql` (README → "Refresh the web schema snapshot").
2. Update `contract.py` and the code that uses the column.
3. Run the tests, then deploy.

## Capacity

Load test (2026-10-18, a Windows laptop running both the server and the load generator, with Postgres in Docker):

- **300 students at once**, half of them in live rooms polling every second, the other half browsing.
- About 160 requests per second in total.
- Median latency 60–190 ms; 95th percentile 0.5–1.1 s.
- 2 dropped connections out of about 7,700 requests.
- The four load-generator processes were close to saturating that machine, so the server's real limit is higher.

Measured cost per request after optimisation:

| Request | CPU per request |
|---|---|
| Live room state | 7 ms |
| Signed-in profile | 8 ms |
| Catalogue / public pages | under 1 ms |

How these numbers keep the cost low:

- Live-room reads are shared between the two players for half a second.
- Signing in costs one query.
- Linux with uvloop on Render is faster than this Windows test machine.

Sizing:

- **Starter (0.5 CPU):** enough for testing and a pilot, roughly up to about 50 debates running at the same time.
- **Standard (1 CPU) or more:** use at launch. Increase `WEB_CONCURRENCY` (workers, default 2) as CPU allows.
  Each worker uses about 100 MB of memory.
- **More instances:** you can add them. Each one keeps its own half-second room cache, so a change can take up
  to half a second to appear on another instance.

Run `scripts/load_test.py` against a staging copy, never production.

## Launch checklist

### Accounts and secrets
- [ ] Rotate the Neon owner password; it was stored in the web repository's `.env.render`, so remove that file
  from the repository (and its git history).
- [ ] The web frontend's `.env.production` exposes `VITE_NEON_DATABASE_URL` and `VITE_GEMINI_API_KEY` in the
  public JavaScript bundle. Remove both from the frontend, rotate the database password and the Gemini key.
- [ ] Create the least-privilege `sym_mobile` database role and switch `DATABASE_URL` to it.
- [ ] Raise the Gemini spend cap to a planned monthly budget, and set the daily budget warning in Settings → AI
  cost estimates.

### Service
- [ ] `ENVIRONMENT=production` for the launch service. This hides `/docs`, keeps email codes out of logs, and
  turns on HSTS.
- [ ] Custom domain (for example `api.symedu.in`) added in Render, and the app rebuilt with it.
- [ ] Resend sender domain verified; a sign-up email arrives within a minute.
- [ ] Both scheduled jobs show recent successful runs.
- [ ] At least two super admins, each with two-step sign-in set up.

### Product
- [ ] Privacy Policy and Terms reviewed by a lawyer (drafts are at `/privacy` and `/terms`, sources in
  `app/legal/`). Decide the age policy: India's DPDP Act treats under-18s as children who need verifiable
  parental consent. Sign-up currently accepts age 8+ and asks under-18s to involve a parent, with no consent check.
- [ ] Firebase/FCM credentials uploaded in Expo for Android notifications.
- [ ] Store listings (see the app repository's `docs/STORE_LISTING.md`).
- [ ] A full live debate between two installed phones, with voice, on the production service.
